# Experiments

The pipeline has five phases. Each phase states what was done, what was measured, and what the
result does and does not establish. Every artefact referenced here ships with this repository
unless stated otherwise.

| Phase | Question | Output |
|---|---|---|
| 1 | Which frameworks leave an attributable trace, and what is that trace? | 64 source audits, 64 indicator inventories, a 610-rule signature set |
| 2 | What does an AI agent's traffic actually look like? | 15 actor captures, 211,547 request records |
| 3 | What does non-AI attack traffic look like? | 1,582 real-attacker actors + 6 scanner actors |
| 4 | Do the signatures survive contact with real traffic? | Two validation corpora, 9,905,794 and 142,705 records |
| 5 | How well does the behavioural detector work, and where does it fail? | Recall with exact intervals, LOFO, ablation, threshold sweep |

## Phase 1 - Source-code audit of the framework landscape

### 1.1 How candidates were extracted

The audit reads the framework's source tree directly, in a fixed priority order, and never
relies on the project's README:

1. **Prompt and skill files** (`.md`, `.txt`, `.yaml` prompt templates, skill libraries,
   playbooks). These matter most: they are where the real curl commands and request templates
   live, because the model composes the request from them at run time.
2. **Tool implementations** - the HTTP client wrappers, the shell tools, the browser drivers.
3. **Attack orchestration** - the agent loop, the planner, the task graph.
4. **Hard-coded literals** - URLs, paths, payloads, user agents, header names.

From each file the audit extracts candidate literals of eight kinds: `UA` (user agent),
`PATH`, `PAYLOAD`, `HEADER`, `CRED`, `OAST`, `TLS`, `PROXY`. Each candidate records its
source location as `file:line`, the stage of the attack it belongs to, and whether it is a
hard-coded constant (**class A**), a string the model generates at run time (**class B**) or a
public tool's user agent (**class C**).

The distinction between A, B and C is the first and most consequential judgement in the audit:

| Class | Meaning | Deployable? |
|---|---|---|
| **A** | Hard-coded in the framework's source | Yes, subject to the usability screen and real-traffic qualification |
| **B** | Composed by the model at run time | Only as a **pattern**, never as an exact string - the version number or identifier changes between runs |
| **C** | A public tool's user agent (curl, sqlmap, ffuf, nuclei, ...) | **No.** Real attackers use the same tools, so a rule on them is a rule on every attacker |

Class C is not a small category. In the nine-framework audit that preceded the corpus, four
frameworks (PentestGPT, VulnBot, CAI's main channel, and parts of PentAGI) had **no
target-facing HTTP client of their own at all**: their entire attack traffic is generated by an
LLM writing shell commands. The consequence - that there is no such thing as a generic "AI
agent user agent" - was the first finding of the study and it still holds.

### 1.2 How each candidate was re-verified

Verification is a separate step, not a by-product of extraction. The procedure:

1. **Line-level re-read.** Every candidate's `file:line` reference is re-opened and the literal
   is confirmed to be present at that line, in that form. A candidate whose location cannot be
   re-found is dropped, not downgraded.
2. **Scope determination.** The audit decides whether the literal is observable **on the target
   side** (`scope = target`) or belongs to a third-party service (`api.github.com`, a
   telemetry endpoint, a package registry), an internal service, an LLM gateway, or is of
   unknown scope. Only `scope = target` literals can become deployment rules: a rule on a
   self-update call to `api.github.com` matches nothing a target ever sees.
3. **Class-A target-side count.** For each framework the audit records how many of its
   indicators are class A *and* target-side. This is the number that predicts whether the
   framework can be attributed at all, and it is published per repository in
   `data/aggregate/framework_coverage_matrix.csv`.
4. **The `not_found` record.** What was searched for and *not* found is recorded explicitly,
   per framework. Examples: "no hard-coded OAST domain anywhere in the repository", "the
   framework's own HTTP client issues zero requests to the target", "every user-agent literal in
   the repository is a generic Chrome string". These negative findings are as load-bearing as
   the positive ones - they are what distinguishes "we found no fingerprint" from "we did not
   look".
5. **Cross-repository uniqueness.** Each literal is checked against the other 63 repositories.
   The `stability` field records the result (`1/1` = unique to this repository, `1/64` =
   found in one repository out of 64, `3/64`, `1/2` = present in one member of a two-repository
   family, and so on). A literal shared by many repositories is not a fingerprint.

### 1.3 Scope of the audit

64 repositories were audited, each with a full audit report and an indicator inventory. The
inventory of candidate repositories is 67 entries: 46 accepted, 7 merged as same-source
derivatives of an already-audited repository, 6 deferred for insufficient evidence, 8 excluded.
The two numbers are not interchangeable and are not conflated anywhere in this repository.

**Result:** 610 rules (272 tier 1, 126 tier 2, 212 tier 3) over 44 distinct framework labels.
The coverage matrix lists 64 audited repositories. The difference is explained in
`FRAMEWORK_COVERAGE.md` section 2.4.

## Phase 2 - Actor-level traffic collection

### 2.1 The target

The evaluation target is a containerised, deliberately vulnerable web application deployed on
the research project's own network, behind an nginx access-audit layer that records one JSON
object per request: timestamp, request id, source address, method, URI, query string, status
code, response bytes, upstream timing, host, user agent, referrer, and the authenticated
identity and role as decoded by nginx from the session token.

The audit layer is the same for every framework, which is what makes the captures comparable.
Container health-check traffic (`/health`, `/healthz`, `/ready`, `/live`) is present in
every capture and is removed before segmentation.

### 2.2 Running each framework

Each framework is installed and driven against the target by the research project, with the
agent's model traffic routed through a local gateway that accepts exactly one model identifier
and returns HTTP 400 `provider_not_allowed` for any other. This makes it structurally
impossible for an experiment to run on a different model than the one the study specifies, and
it means the credentials the framework writes into its own configuration are irrelevant - the
gateway injects the working ones.

Per-framework environment notes (image names, API prefixes, login names, framework-specific
opt-in flags, non-private address ranges used to satisfy scope guards) are recorded with each
audit and summarised in the blocking-reason column of `FRAMEWORK_COVERAGE.md`.

Two scope-guard decisions are worth recording because they are the kind of thing that gets
quietly done wrong:

* Where a framework ships an **official** opt-in for scanning a self-hosted local application
  (`XALGORIX_ALLOW_LOCAL_TARGETS=1`), that switch was used. The framework's own documentation
  describes it as the supported way to point the tool at a local instance.
* Where a framework's guard is **fail-closed with no official opt-in** (guardian-cli's built-in
  blacklist refuses every local address), the framework was **abandoned rather than bypassed**.
  It appears in the matrix as `partial` with the reason recorded.

### 2.3 How actors were separated

Actor separation is the one methodological choice that most affects the numbers, so it is
stated precisely.

* **On the positive side**, each framework ran in its own deployment with its own source
  address, in its own time window. The address is the grouping key and never becomes a feature.
  Within one framework's run, the actor is one contiguous burst (session mode, 600 s gap).
* **On the negative side**, real internet attackers cannot be given addresses, so their actors
  are grouped by source address within a fixed 10-minute window (window mode). Grouping by
  address alone would collapse a persistent attacker's many waves into a single actor, which is
  a much easier target than the defender actually faces.
* **Ground-truth labels are never features.** The labelling used for evaluation is by
  (capture, source address) and by user agent, and is applied only when computing metrics.
  It never enters the feature vector.

The two corpora therefore use different actor definitions, and both are reported. This is a
deliberate asymmetry: the positive side is a controlled single-actor run, the negative side is
the uncontrolled population the method has to survive.

file. The scored actors are on different source addresses and are therefore disjoint, so no
measurement is affected. A reader who trains on `data/positive/` and evaluates on
`data/negative/` must remove the nested records first, or restrict the negative set to
request identifiers that do not appear in the positive capture. This is stated here so that the
overlap is not a surprise.

## Phase 3 - Negative-sample construction

A detector that has only ever seen positive traffic is untested. Three negative sources were
built, each for a specific reason, and each with a documented limitation.

### 3.1 N1 - honeypot field data

| Property | Value |
|---|---|
| Source | Three honeypot servers (armbian, an Alibaba Cloud host and a Tencent Cloud host) |
| HTTP events | 4,714 (aurelia 44, juiceshop 284, h0neytr4p 4,670) |
| Protocol-level events | 251,236 (cowrie 181,816, dionaea 69,014, adbhoney 437) |
| Time span | 4 days |
| Distinct source addresses | 929 (HTTP), 1,325 (protocol) |
| Actors after segmentation | 91 (per source address), 80 (per address + 10-minute window) |
| Contains 2xx responses | **yes** (749 2xx) |

**Why it is needed.** It is the only negative source with successful responses *and* with a
varied population: real sqlmap, zgrab, IoT botnets and human probing. It is what allows the
2xx-dependent features to be exercised at all.

**Its limits, stated.** The 4,670 h0neytr4p events lack user agent and status code, so they
cannot be used for feature extraction. 827 of the 991 sessions contain a single request and
only 28 are long sessions. And the 4-day window contains **no attack that could be confirmed to
be AI**, so this source cannot be used to train anything. Its measured false-positive rate at
tau 0.35 is 0/4 attacker-class actors - a sample far too small to be a rate.

### 3.2 N2 - 30-day WAF attack log

| Property | Value |
|---|---|
| Source | ModSecurity with the OWASP Core Rule Set, audit log |
| Transactions | 151,011 |
| Actors per source address | 2,794; attacker-class (browser or tool user agent) 1,582 |
| Actors per address + 10-minute window | 2,027; attacker-class 1,780 |
| Contains 2xx responses | **no - zero** |
| False positives at tau 0.35 | 43 of 1,582 (2.718%, Wilson 95% [2.02%, 3.64%]) |

**Why it is needed.** Scale. It is two orders of magnitude larger than N1 and it is entirely
made of real internet attackers hitting a production WAF.

**Its limit, and it is a serious one.** A WAF audit log records only transactions that
**triggered a WAF rule**. Successful requests are not in it. Three consequences, all of which
are documented in `LIMITATIONS.md` section 5.1:

* The 8 `f8_egress_*` features are identically zero for every actor in this population.
* E12 (`f6_verify_backtrack`) can never fire, because its 2xx denominator is zero. Its
  measured 0% negative coverage is an artefact, not a property - re-measured on a population
  that does contain successful responses, E12 fires on 8 of 8 scanner actors.
* The "browser" class means the user-agent blob looked like a browser. On an attack
  transaction that does not establish that a human was operating it.

### 3.3 N3 - real scanners against the evaluation target

| Property | Value |
|---|---|
| Method | 10 real scanning tools placed in 12 independent containers, each with its own source address on the target's network |
| Records | 12,666 (1,084 2xx, 11,488 4xx) |
| Actors | 8 per source address, of which 6 are attacker-class; 10 per address + window, of which 7 |
| False positives at tau 0.35 | 4 of 6 attacker-class actors (66.67%) |
| Published subset | 999 records across 6 actor captures |

**Why it is needed.** It is the only negative population that is simultaneously (a) attack
traffic, (b) tool-driven, and (c) rich in successful responses. N1 has 2xx but is not
tool-driven; N2 is tool-rich but has no 2xx.

**Its limit, stated plainly.** The released subset is **ffuf-dominated**: 910 of the 999
published records carry `Fuzz Faster U Fool v2.1.0-dev`. The remaining 89 are curl (35),
python-requests (13), masscan (6), Nikto (6), browser-masquerade user agents (27),
Go-http-client (2) and wget (2). No gobuster, nuclei, dirb or nmap record survives into the
released set; in the full 12,666-record source capture sqlmap contributes a single request.
The 66.67% figure therefore characterises ffuf-style enumeration behaviour, not a balanced
multi-tool population, and the sample of 6 actors gives a wide Wilson interval of
[30.0%, 90.3%].

Two actors of the source file are **not** released and are listed under
`excluded_crawler_class_actors` in `data/negative/_index.json` with their scores: the
long-lived tool container at `172.34.0.1` (11,582 records, score 0.7342) and `172.34.0.14`
(85 records, score 0.5423). Both are classified as crawler rather than attacker because their
user-agent blobs mix scanner traffic with public search-engine user agents, and both are
**false positives** of the detector. Excluding them keeps the published figure at 66.67% for
the attacker-class population rather than 6 of 8 = 75.00% for the whole file; the excluded
scores are published so that the choice is auditable.

### 3.4 The earlier 56-actor negative set, and why its number was withdrawn

The first version of this study measured the false-positive rate on 56 honeypot sessions and
reported "FPR < 5.36%" by the rule of three. That figure was **withdrawn and replaced** when
the negative population was enlarged, because 56 actors support a bound of about 5% and
nothing finer. The replacement figure, 2.718% with a Wilson interval of [2.02%, 3.64%] on
1,582 actors, is larger and better founded. The general lesson is recorded because it applies
to any false-positive claim in this field: a rate quoted without its denominator and interval
is not a measurement.

## Phase 4 - Validation of the signature set on real traffic

Static source audit cannot tell whether a rule will match ordinary traffic. Two corpora were
used, and each proves something different.

### 4.1 Public internet background traffic

| Property | Value |
|---|---|
| Dataset | `burpheart/Internet-background-noise` |
| Records | 9,905,794 |
| Distinct source addresses | 80,987 |
| Distinct user agents | 80,764 |
| Fields available | full request headers and request bodies |
| Tier-1 rules matched | **0** |
| Rules matched at any tier | 16, all tier 2 or tier 3 |

**What it proves.** A tier-1 rule set does not fire on ordinary internet traffic, including
crawlers, browser farms and background scanners. It also produces the combinatorial figure
that makes actor-level alerting operational: exactly **1** source address out of 80,987 matched
two or more rules, so alerting on actors that match two or more rules produces one alert per
80,987 addresses.

**What it does not prove.** It does not prove the rules will not fire on traffic that is itself
an attack. The corpus is background noise, not attacks - which is exactly why a second corpus
was needed.

### 4.2 Real WAF attack transactions

| Property | Value |
|---|---|
| Dataset | ModSecurity OWASP CRS audit log, 30 consecutive days |
| Transactions | 142,705 |
| With a user agent | 139,598 |
| With a request body | **0** - the audit format does not record bodies |
| Method distribution | GET 127,567, POST 14,484, HEAD 499, CONNECT 6, PROPFIND 71, OPTIONS 12, PUT 47, PATCH 6, DELETE 12, others 2 |
| Tier-1 rules matched | **0** |

**What it proves.** A tier-1 rule set does not fire on 142,705 transactions that a production
WAF classified as attacks. This is the corpus that exposed the defect the study had to fix:
before the tier corrections, 11 tier-1 rules matched this traffic - `Upgrade-Insecure-Requests`
alone 9,280 times, `Accept-Language` 5,000 times, `Content-Type` 2,754 times,
`CloudFront-Viewer-Country` 171 times - all of them generic HTTP headers or CDN-injected
headers that a real attacker sends like anybody else.

**What it does not prove.** Because no transaction carries a request body, the 150 body-field
tier-1 rules could not be exercised against this corpus at all. Their zero-hit result comes
from the 9.9M-record scan, which does carry bodies. This is a gap in the evidence, not a clean
pass, and it is recorded as such in `LIMITATIONS.md` section 5.5.

### 4.3 The scanner hard-negative gate

The third gate scans the rule set against the real scanner traffic of phase 3.3 and requires
zero tier-1 hits. The released repository re-runs this gate on the shipped data:

```bash
python -m research.ci.selftest_rules
```

The gate has three parts: a synthetic benign browser request must match zero tier-1 rules; a
synthetic request carrying a known tier-1 literal must match that rule and only that rule; and
every published scanner capture must produce zero tier-1 hits.

## Phase 5 - Statistical evaluation

### 5.1 Leave-one-framework-out

Hold one framework out completely; calibrate the decision threshold on the remaining
frameworks only (the lowest score that still keeps them at full recall); apply that threshold
to the held-out framework; count true and false positives against the negative population.

The **number of folds is the number of frameworks**, not the number of captures. This is the
single most important methodological correction the study made: the earlier framing of
"LOFO 6/7 = 86%" implied seven independent trials, when the fold count was really four
frameworks. The correct statement of generalisation strength is `0.05^(1/k)` in *k*, the
framework count - and it moves only when a new framework is added.

### 5.2 Family ablation

For each actor, remove one family's weight from the noisy-OR product and re-test against the
threshold. The reported figure is the exact fraction still detected. This is a deterministic
ceiling, not a sampled estimate: "if the deployment's logs cannot supply this family, the
recall cannot exceed this". The implementation is in `research/evaluation/family_ablation.py`.

### 5.3 Threshold sweep

Sweep the threshold over the positive and negative populations simultaneously and report
recall and false-positive rate at each point, so that the trade-off is visible rather than
asserted. The implementation is in `research/evaluation/threshold_sweep.py`, and it
cross-checks the recomputed false-positive counts against the shipped
`data/aggregate/threshold_fpr_tradeoff.json` and prints OK or MISMATCH for each threshold.

### 5.4 Interval estimation

| Estimator | Used for | Implementation |
|---|---|---|
| Clopper-Pearson (exact, two-sided) | Segment-level and framework-level recall | `research/evaluation/stats.py` |
| Jeffreys (Beta(1/2,1/2) posterior, two-sided) | The same, as a wider companion interval | same |
| Wilson score interval | The false-positive rate | same |
| Rule of three (3/n) | An upper bound when zero events are observed | same |
| `0.05^(1/k)` | The one-sided lower bound on "all k frameworks detected" | same |

The Beta quantiles are computed with SciPy when it is installed and with a pure-Python
continued-fraction implementation otherwise; the two agree to 1e-12, so the released pipeline
has no third-party runtime dependency.

### 5.5 The null-hypothesis check that shaped the method

Before the rule set was trusted, the study asked whether its result was a property of the
method or merely of the data being easy to separate. Three randomisation tests were run:

| Test | Result |
|---|---|
| Rule conditions randomised, weights and structure kept | median AUC 0.5893; the real rule set at the 96.0th percentile |
| Thresholds randomised, conditions and weights kept | median AUC 0.9940; the real rule set at the 67.7th percentile |
| Single rules used alone as alerts | false-positive rates of 1.8% to 26.8% on the negative population; **fused: 0** |

The third row is the load-bearing result. Every individual rule misfires on real traffic;
their errors do not overlap, and requiring several to fire at once removes the false positives
while keeping the recall. This is why the method is a multi-rule fusion rather than a
single strong signature, and it is why the fusion's exact algebra (section 4 of
`METHODOLOGY.md`) matters.

The second row is the cautionary one: **AUC alone does not demonstrate that a method works.**
A random threshold set reaches a median AUC of 0.994 on this data. Only the false-positive
counts and the interval estimates carry evidentiary weight.

### 5.6 Reproducing the whole evaluation

```bash
cd ai-agent-attack-signatures

python -m research.ci.check_headline_numbers   # validates every headline figure
python -m research.evaluation.evaluate_detection
python -m research.evaluation.false_positive_eval
python -m research.evaluation.lofo
python -m research.evaluation.family_ablation
python -m research.evaluation.threshold_sweep
python -m research.ci.selftest_rules
```

Runtime: seconds on one CPU core. No GPU, no network, no credentials.
